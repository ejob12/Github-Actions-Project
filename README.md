# Bank App CI/CD on AWS

This repository contains a Java 17 / Maven bank application and GitHub Actions workflows for building, scanning, analyzing, containerizing, and deploying it.

## Workflow setup history

1. Create an Ubuntu EC2 instance to act as a GitHub Actions self-hosted runner.
2. In GitHub, open the repository's **Settings → Actions → Runners → New self-hosted runner**, select **Linux**, and follow the commands GitHub provides to install and register the runner. Keep the runner service running.
3. Push a change to the repository to start the workflow. If the build fails because Maven is missing on the runner, install Java and Maven using the repository script:

   ```bash
   chmod +x maven-install.sh
   ./maven-install.sh
   chmod +x install-maven.sh
   ./install-maven.sh
   ```

   `maven-install.sh` generates `install-maven.sh`; the second pair of commands runs the generated installer. Verify the installation with `java -version` and `mvn -version`.
4. The workflow can then reach its SonarQube analysis. Create a separate Ubuntu EC2 instance for SonarQube and run the repository's installer script:

   ```bash
   chmod +x sonarqube-install.sh
   ./sonarqube-install.sh
   ```

   The script creates and runs `install-sonarqube-latest.sh`, which starts SonarQube and PostgreSQL with Docker Compose. Wait for SonarQube to become available at `http://<SONARQUBE_EC2_PUBLIC_IP>:9000`, sign in, change the initial password, and generate an analysis token in SonarQube.
5. Add the SonarQube token and URL to the repository's GitHub Actions configuration as described below.
6. When a run fails on the self-hosted runner with `unzip: command not found`, install the missing Ubuntu package on that runner:

   ```bash
   sudo apt-get update
   sudo apt-get install -y unzip
   unzip -v
   ```

   This is needed by the workflow's AWS CLI installation step, which downloads and extracts the AWS CLI zip archive.
7. The `cicd-3.yml` workflow builds and pushes the Docker image as `ejob12/bankapp:latest`. Configure its Docker Hub credentials in GitHub as shown below.

## GitHub Actions secrets and variables

In the repository, go to **Settings → Secrets and variables → Actions**. Add secrets under **Secrets** and non-sensitive values under **Variables**.

| Type | Name | Value |
|---|---|---|
| Secret | `SONAR_TOKEN` | Your SonarQube analysis token |
| Variable | `SONAR_HOST_URL` | `http://13.51.107.213:9000` |
| Secret | `DOCKERHUB_TOKEN` | Your Docker Hub access token with read/write permissions |
| Variable | `DOCKERHUB_USERNAME` | `ejob12` |
| Secret | `AWS_ACCESS_KEY_ID` | Access key for an AWS IAM identity authorized to access the EKS cluster (needed by the deployment job) |
| Secret | `AWS_SECRET_ACCESS_KEY` | Secret access key for the same AWS IAM identity (needed by the deployment job) |
| Secret | `EKS_KUBECONFIG` | The complete, raw YAML contents of the kubeconfig file for your EKS cluster (needed by the deployment job) |

Do not put tokens, access keys, or kubeconfig contents in the repository or in workflow files. Use an Elastic IP or another stable endpoint for SonarQube if its EC2 public IP may change, and restrict access to port `9000` to trusted sources in the EC2 security group.

### Add the EKS kubeconfig as a GitHub secret

The current deployment workflow writes `${{ secrets.EKS_KUBECONFIG }}` to `$HOME/.kube/config`. The secret must therefore contain the kubeconfig's **raw YAML**, not a base64-encoded value.

1. On a trusted machine with AWS CLI configured for an IAM identity authorized for the cluster, generate or update the kubeconfig. Substitute your EKS cluster name:

   ```bash
   aws eks update-kubeconfig --region ap-south-1 --name <EKS_CLUSTER_NAME>
   ```

2. Check that the selected context points at the intended cluster:

   ```bash
   kubectl config current-context
   kubectl config view --minify
   ```

3. Open `~/.kube/config` in a text editor and copy its complete YAML contents. In GitHub, choose **Settings → Secrets and variables → Actions → New repository secret**, name it `EKS_KUBECONFIG`, and paste the YAML as the secret value. Keep its indentation and line breaks.
4. Add `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY` for the IAM identity the workflow will use. The workflow configures these credentials before calling `kubectl`. The IAM identity must be granted access to the EKS cluster (for example, through an EKS access entry) and Kubernetes permissions to apply the resources in `ds.yml`.
5. On a successful deployment, verify the resources with `kubectl get deployments,services` using the same cluster context.

The kubeconfig generated by `aws eks update-kubeconfig` uses the AWS CLI `exec` credential plugin. The deployment job must have AWS CLI installed and configured with the IAM credentials above; the workflow installs the AWS CLI and configures AWS credentials before invoking `kubectl`.

> **Deployment workflow note:** The Kubernetes deployment job in `.github/workflows/cicd-3.yml` is currently commented out, so that workflow will not deploy to EKS until the job is enabled. Its AWS region is currently `ap-south-1`. The application image in `ds.yml` is `ejob12/bankapp:latest`, matching the image built and pushed by `cicd-3.yml`.

## Workflows

The workflows are in `.github/workflows/`. `cicd-3.yml` runs on pushes to `main` and uses a self-hosted runner. Its jobs compile and scan the project, run Maven tests, perform SonarQube analysis, build and scan a Docker image, and push the image to Docker Hub. The Kubernetes deployment job is commented out as noted above.
